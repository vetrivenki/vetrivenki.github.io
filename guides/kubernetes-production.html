1. Production architecture and request flow

End-to-end application traffic

DNS and external load balancer route requests through an ingress controller or Gateway API to a Kubernetes

Service, which selects ready application Pods. Pods may call other services, databases, queues and external

APIs.

GitOps deployment flow

Developer commit -> CI tests/builds/scans image -> immutable image published -> GitOps configuration

updated -> Argo CD compares desired state -> Kubernetes API accepts resources -> Deployment controllers

reconcile replicas.

Scaling flow

HPA scales replica counts using metrics; KEDA supplies event-driven scaling based on queue length or other

triggers; scheduler places Pods; Karpenter adds worker nodes when Pods cannot be scheduled.

2. Control plane and EKS

API server

Authenticated and authorized interface for Kubernetes resource operations. Troubleshoot API access, RBAC,

admission webhooks, latency and throttling.

etcd

Stores cluster state. AWS manages etcd and control-plane nodes in Amazon EKS; customers do not directly

manage the EKS etcd servers.

Scheduler and controllers

Scheduler chooses eligible nodes for Pending Pods. Controller manager, omitted from the diagram, reconciles

Deployments, nodes and other Kubernetes objects.

Worker nodes

EC2 nodes run kubelet, containerd, CNI components and application Pods. Inspect node readiness, IP availability,

IAM permissions, node bootstrap, CPU, memory and disk pressure.

3. GitOps, CI/CD and Argo CD

Delivery design

Keep application source, built images and deployment configuration separately governed. Prefer immutable

image digests, code review, security scanning and auditable promotion.

Argo CD troubleshooting

Check Application health and sync status, manifest rendering, Helm values, repository access, cluster RBAC,

missing CRDs, unhealthy Deployments and admission failures.

4. Secrets and Kyverno policy

External Secrets Operator

Reads values from an external provider and commonly synchronizes them into Kubernetes Secret objects.

Configure workload identity, scoped provider permissions and rotation.

Secrets Store CSI Driver

Mounts externally managed secrets as files in Pods, with optional synchronization to Kubernetes Secrets. Choose

integration based on application behavior and rotation needs.

Kyverno

Admission policies can validate, mutate, generate and report on resources. Enforce non-root containers,

approved registries, resource limits and required labels. Test in audit mode before enforcement.

Security boundaries

Use Kubernetes RBAC, EKS Pod Identity or IRSA, KMS encryption, network segmentation, admission policies,

image scanning and CloudTrail/EKS audit logs.

5. HPA, KEDA and queue-driven scaling

HPA

Uses resource, custom or external metrics to change replica count within configured bounds. CPU-based

utilization requires appropriate resource requests and a working metrics pipeline.

KEDA

Uses event-source scalers such as SQS or Kafka to control workloads. A ScaledObject commonly manages an

HPA; depending on scaler it can scale workloads to zero.

Backlog scenario

Queue backlog grows -> KEDA calculates desired consumer replicas -> HPA adjusts workload replicas ->

scheduler places Pods -> Karpenter provisions nodes when needed. Watch database and queue-processing limits

before increasing concurrency.

Scaling failure

Check HPA conditions, metrics server/adapter, KEDA trigger authentication, pending Pods, quota, Karpenter

constraints and EC2/subnet capacity.

Karpenter observes unschedulable Pods, evaluates NodePool and EC2NodeClass requirements, and provisions

NodeClaims/EC2 instances compatible with workload requirements.

Common failures

Restrictive instance families, AZ constraints, capacity unavailability, EC2 quotas, exhausted subnet IPs, IAM

policies, wrong subnet/security-group discovery and failed node registration.

EKS distinction

EKS Auto Mode manages node provisioning differently from a self-managed Karpenter installation; do not

assume the same controller operations in both modes.

7. Service mesh, ingress and NetworkPolicy

Ingress and service routing

An ALB/ingress or Gateway routes incoming traffic to Kubernetes Services and ready endpoints. Verify listener,

health checks, target types, port mappings and DNS.

Istio versus Linkerd

These are alternative mesh products providing service identity, mutual TLS, telemetry and traffic controls. Do not

treat them as one combined mandatory component.

NetworkPolicy

NetworkPolicy resources are enforced by a compatible CNI/policy engine. They are separate from mesh

authorization policies and must be tested for DNS and dependent-service access.

Mesh incident

mTLS mismatches, certificate rotation, proxy exhaustion and retry storms can cause 503s or elevated latency.

Correlate mesh metrics and traces with application telemetry.

8. Observability: Prometheus, Grafana, Jaeger

Prometheus

Collects and stores time-series metrics; monitor pod restarts, CPU throttling, request rate, latency, errors, node

pressure, HPA and Karpenter activity.

Grafana

Displays dashboards across configured metrics, logs and traces backends. Create customer-facing golden-signal

and cluster-capacity dashboards.

Jaeger and OpenTelemetry

Jaeger is a tracing backend/UI. Applications and proxies emit traces, often via OpenTelemetry SDKs and

collectors; Jaeger is not itself a required sidecar.

9. High availability and disaster recovery

Multi-AZ

Distribute critical replicas across AZs, maintain spare capacity, use load-balancer health checks and test

zone-loss scenarios.

Disruption budgets

PodDisruptionBudgets constrain voluntary evictions; they do not prevent involuntary failures such as an AZ

outage.

Storage and database

EBS volumes are AZ-bound. Stateful workload recovery requires storage-specific planning, and database failover

must be verified separately.

RTO and RPO

RTO is maximum acceptable restoration time; RPO is maximum acceptable data-loss window. Measure actual

outcomes through regular exercises.

10. Five production troubleshooting scenarios

Pods CrashLoopBackOff

Check kubectl describe, previous logs, exit codes, probes, OOMKilled events, secrets and recent releases.

Mitigate with safe rollback or evidence-based configuration/resource correction.

Pods Pending and Karpenter fails

Inspect scheduler events, NodePools, NodeClaims, EC2NodeClass, capacity, quotas and subnet IPs. Fix

constraints and confirm new nodes join.

ALB 502/503

Inspect target health, ingress, Service endpoints, backend port, readiness, TLS and application logs. Correct the

specific routing/health failure and verify requests.

Queue backlog despite HPA

Validate KEDA trigger/credentials, metrics, desired replicas, Pod readiness, node provisioning and consumer

processing throughput. Avoid overwhelming downstream services.

AZ outage

Verify healthy AZ target capacity, pod distribution, persistent volumes, database availability and recovery. Test

application transactions and recovery objectives.

11. Senior engineer interview questions

Kubernetes Production Infrastructure - Detailed Guide 5

<PARSED TEXT FOR PAGE: 6 / 7>

How are HPA, KEDA and Karpenter different?

HPA scales Pod replicas; KEDA supplies event-driven metrics/triggers and commonly manages HPA; Karpenter

provisions compute nodes.

What happens when the API server is unavailable?

Existing workloads can often keep serving, but new scheduling, management and reconciliation operations may

be disrupted.

Does a PDB guarantee HA?

No. It governs supported voluntary disruptions, not node or AZ failures.

What if Pods are Pending after HPA scales?

Desired replicas are not schedulable capacity. Check requests, affinity, taints, quotas, storage and Karpenter.

Why is a NetworkPolicy not enforced?

The selected CNI may lack enforcement or selectors/rules may not match the intended traffic.

How do you design zero-downtime deployment?

Use readiness/startup probes, multiple replicas, safe rolling-update settings, disruption budgets, capacity

headroom and health-based rollback.

How do you measure reliability?

Define SLIs/SLOs for availability, errors and latency, monitor error budgets and validate incident recovery.

How do you handle production incidents?

Assess customer impact, declare severity, coordinate mitigation, use telemetry for evidence, restore service,

communicate and track preventive actions.

13. Production readiness checklist

• Multi-AZ node and Pod distribution tested

• IAM, RBAC, Pod Identity/IRSA and secrets reviewed

• Image scanning and admission policies enforced

• GitOps drift alerts and rollout rollback tested

• HPA, KEDA and Karpenter scale-out tested

• Prometheus alerts, Grafana dashboards and tracing validated

• Backups, storage restoration and DR rehearsed

• Runbooks, ownership, incident communications and SLOs documented
