Kubernetes Health Probes

Readiness vs Liveness vs Startup | Production operations, YAML and interview scenarios

Venkatesan Vetrimurasu · Venkat's Tech Lab

1. Readiness Probe

Answers: Can this container receive traffic now? When readiness fails, the Pod is removed from ready Service endpoints; the container is not restarted solely because of readiness failure. Use it for local initialization, capacity to serve requests, and critical application readiness. Avoid treating every shared downstream outage as readiness failure, which can remove all replicas from service.

readinessProbe:
  httpGet:
    path: /health/ready
    port: 8080
  periodSeconds: 5
  timeoutSeconds: 2
  failureThreshold: 3

2. Liveness Probe

Answers: Is the container healthy enough to continue running? Repeated failures cause kubelet to restart the container. Use it for unrecoverable deadlocks and hangs, not for a shared database or external API that may temporarily fail.

livenessProbe:
  httpGet:
    path: /health/live
    port: 8080
  periodSeconds: 10
  timeoutSeconds: 2
  failureThreshold: 3

3. Startup Probe

Protects slow-starting applications. Until the startup probe succeeds, kubelet suppresses liveness and readiness probes. Configure failureThreshold × periodSeconds to allow realistic startup duration.

startupProbe:
  httpGet:
    path: /health/startup
    port: 8080
  periodSeconds: 10
  failureThreshold: 30

4. Failure Behavior

Readiness fails: the Pod remains running but stops receiving traffic through Services that rely on ready endpoints.

Liveness fails: kubelet restarts the affected container after the configured consecutive failures.

Startup fails: kubelet restarts the container if startup does not succeed within the allowed failure budget.

5. Production Troubleshooting

kubectl -n production get pods -o wide
kubectl -n production describe pod <pod-name>
kubectl -n production logs <pod-name> --previous
kubectl -n production get endpointslices
kubectl -n production get events --sort-by=.lastTimestamp

Check probe failure events, response codes, actual health endpoints, application logs, recent deployments, CPU throttling, resource pressure, and ingress or ALB target health.

6. Common Mistakes

Too-short timeouts, using the same endpoint for different semantics, probing shared dependencies in liveness, omitting startup probes for slow boot, wrong path/port, and treating probes as complete end-to-end monitoring.

7. Senior Interview Scenario

Question: After an Argo CD deployment, Pods show Running but users see intermittent HTTP 503. How do you troubleshoot?

Answer: Check Pod readiness and events, Service EndpointSlices, ALB/ingress health, application startup logs and recent rollout changes. If new replicas are unready, pause or revert the rollout safely, verify real user requests, correct the probe or startup timing, and add deployment health gates.

8. Interview Quick Questions

Readiness vs liveness? Readiness controls Service traffic eligibility; liveness triggers container restart after repeated failures.

Why startup? Prevents premature failures during slow initialization.

Can liveness cause an outage? Yes, aggressive thresholds or shared dependency checks can restart otherwise functional replicas.

What if every Pod is unready? The Service may have no ready endpoints and traffic can fail even while Pods show Running.
